# PRD: The Classics Reading Desk

## Problem Statement

Readers who want to follow the Ten-Year Great Conversation need a durable working desk, not a teaching website or a disposable checklist. The reading path spans years, hundreds of Works, many Great Authors, Syntopicon terms, notes, research sessions, drafts, and private progress. Without a single controlled app, the reader has to scatter the work across bookmarks, notes apps, spreadsheets, search tabs, subscriptions, and memory.

The reader needs The Classics to point them toward the right Works, authors, notes, terms, and outside resources while preserving direct reading as the center of the experience. The app must stay useful for repeated personal use, survive without a paid note subscription, and keep Reader Data under the reader's control.

## Solution

The Classics is a static, no-build reading desk for the Great Books and the Ten-Year Great Conversation. It gives the reader a navigable Library, Bookclub reading plan, Great Authors index, Syntopicon Glossary, Notes Drawer, Conversation Desk, Study Timer, optional Cloud Sync, and optional Donation support.

The app should make the next reading action obvious: find a Work, see where it sits in the plan, choose a Reading Stage or task, open high-quality Resource Links, capture Notes, and shape those Notes into a private or eventual Public Voice through the Conversation Desk. Guidance supports the book; it does not replace the book.

## User Stories

## Implementation Decisions

- Preserve the static app shape. The app remains a browser-served reading desk with no build step unless the user explicitly asks for one.
- Use vanilla browser JavaScript and DOM APIs. Do not introduce a framework just to complete the current product direction.
- Keep the app shell responsible for metadata, static markup, Firebase bootstrap, stylesheet loading, and script loading.
- Keep state in a single shared app state object populated from local persistence and remote data during startup.
- Keep local persistence as the default Reader Data layer for progress, stages, dates, notes, timer settings, user profile, payment summaries, and Conversation Desk drafts.
- Keep Cloud Sync optional. Signed-in readers can sync private Reader Data; unsigned readers can still use the core app locally.
- Use Firebase Auth for account identity and Firestore for private synced Reader Data.
- Keep Conversation Desk private by default. Visibility values may prepare for sharing later, but public publishing is not part of this PRD.
- Keep MortAI as editorial help inside Conversation Desk, not as a replacement for reading or the reader's argument.
- Keep donation flow outside the app through a Stripe-backed worker or checkout endpoint. The app should not process payment credentials.
- Treat the Library, Bookclub, Great Authors, Glossary, Getting Started Guide, Notes Drawer, Conversation Desk, Study Timer, and Donation flow as user-facing surfaces that should remain navigable from the reading desk.
- Load Great Books catalog data, Bookclub plan data, reading guide rows, glossary terms, and Syntopicon data from static files.
- Normalize catalog and plan matching so Work metadata can be joined from multiple static data sources.
- Preserve Resource Links as outbound research launchers. Resource queries may be shaped by Work, author, title, Great Idea, Reading Stage, Bloom-style learning goal, and custom search text.
- Preserve the newspaper-like reading-desk identity. The interface should feel scholarly, direct, and tool-like, not like a marketing site.
- Keep implementation changes modular and behavior-focused. Refactors should be justified by a user-visible path or a clear maintainability seam.
- Do not make the app a teaching website. Onboarding and glossary context may explain navigation and terms, but the product should point readers toward the books and outside research rather than replacing them.
- Keep Reader Data portable through import/export where practical, especially Notes.
- Keep the reset profile behavior explicit and destructive only after confirmation.
- Keep future project-execute work blocked until the vertical slice breakdown is explicitly approved.

## Testing Decisions

- Test at the highest user-visible seam available: serve the static app over a local HTTP server, load the page in a browser, and verify the behavior a Reader experiences.
- Use JavaScript syntax checks across source modules as the quick deterministic check after code changes.
- Prefer behavioral tests and manual smoke scripts that exercise Library, Bookclub, Great Authors, Glossary, Notes, Conversation Desk, timer, auth display, sync status, and donation modal entry points.
- Data-loading tests should verify that catalog, reading plan, reading guide CSV, glossary data, and Syntopicon data can load and produce useful UI state.
- Persistence tests should verify local save/load behavior for progress, Reading Stages, dates, Notes, timer settings, user profile, and Conversation Desk drafts.
- Cloud Sync tests should focus on externally visible outcomes: local-only use works, sign-in enables sync, remote data merges with local data, deleted Notes stay deleted, and Conversation Desk sync does not overwrite newer local drafts.
- Resource Link tests should verify generated URLs and visible action sets for several Reading Stages without asserting unrelated DOM internals.
- Accessibility smoke tests should check keyboard navigation, visible focus, modal/drawer open and close behavior, semantic labels, and mobile viewport layout.
- Donation tests should verify amount selection, custom amount validation, signed-in profile attachment when available, and graceful error handling if the checkout endpoint fails.
- Existing prior art for checks includes the repository's module syntax check command and local HTTP server workflow.

## Out of Scope

- Replacing the static app with a full SPA framework.
- Adding a build pipeline as part of the current idea-init output.
- Turning the app into a course, lesson site, or internal teaching content library.
- Hosting full copyrighted Works inside the app.
- Making Conversation Desk drafts public without a separate privacy, moderation, and publishing decision.
- Processing payment card data directly in the app.
- Reworking DNS, hosting, Firebase project ownership, or mail provider configuration.
- Creating ADRs for routine implementation details.
- Publishing AFK slice files before the slice breakdown is approved.
